# Enforcement — what actually backs each claim

This repo states a lot of invariants — in `CLAUDE.md`, `agent-firm/policy/never-rules.yaml`, agent
prompts. Some are backed by a script that fails closed. Some are backed by a permission rule Claude
Code itself enforces. Some are backed by nothing but the model reading the instruction and complying.
Those are very different guarantees, and conflating them is exactly the kind of overclaiming this
firm's own Definition of Done prohibits elsewhere. This table says which is which.

**This table is hand-maintained and is not guaranteed complete.** It covers the load-bearing claims,
not provably every sentence in the repo; nothing mechanically diffs claims against rows, so a new
invariant can be stated somewhere and never land here. Rows have in fact been added after the fact
(traceability, no-self-approve, the `bin/` regression suite). Read it as the best current map, and
apply the rule at the bottom: **an invariant with no row here is tier 4 until someone shows otherwise.**

**Enforcement tiers, strongest to weakest:**
1. **Mechanical, always-on** — a script or permission rule that runs regardless of what the model
   decides, and fails closed on uncertainty.
2. **Mechanical, opt-in** — a real control (sandbox, firewall) that only applies if you turned it on.
3. **Mechanical, unverified** — configuration that's *present* but was never confirmed to behave as
   intended against the live system (see the two flagged rows below for exactly what "unverified" means).
4. **Prompt-only** — an instruction the model is expected to follow. No script or permission rule
   backs it. The model's own judgment is the entire mechanism.

| Every acceptance criterion is covered or justified before the Final gate (the traceability gate) | 1 (for eval runs) / 4 (for a live engagement) | `firm-traceability-check` cross-references the ids in `01-acceptance-criteria.yaml` against `acceptance_criteria_coverage` in `08-qa-verdict.json`. A criterion absent from the verdict fails; `covered: no` fails unless it carries a written justification in `evidence`; **`covered: partial` fails the same way** — a half-covered criterion with nothing said about the other half is a gap, not a pass. When gaps exist it prints `TRACEABILITY: INCOMPLETE`, never `PASS`. Fails closed at `CANNOT VERIFY` (**exit 2**) if `criteria:` is present but no ids could be parsed, so a format it can't read is never a vacuous pass. **The cross-reference runs in both directions.** A coverage entry naming an id that *no* criterion declares is **exit 2**, not a pass and not a coverage failure: it is evidence the verdict was written against a *different* criteria set, and once that is true the entries whose ids *do* match are untrustworthy too (an id is only a label). Before that check existed, a verdict claiming coverage for `AC-999-DOES-NOT-EXIST` **passed** — while printing the `acceptance criteria: 2  verdict coverage entries: 4` mismatch it then ignored — so the gate could not tell "this verdict describes this run" from "this verdict describes some other run". An *empty* coverage list is unaffected and stays exit 1 (coverage is zero, which is a question the gate can answer). Exit codes are a three-way classification — `0` evaluated/acceptable, `1` evaluated/coverage INADEQUATE, `2` CANNOT EVALUATE (bad or unreadable inputs, zero criteria, an uninterpretable coverage value, **a coverage entry naming an undeclared id**, **no usable YAML parser**, an internal error) — because callers *invert* this gate and must not read "the checker blew up" as "coverage correctly failed". The parser state is classified the same way, and with the same `importlib.util.find_spec("yaml")` discriminator, as in `firm-check-assertions` (row below): pyyaml **absent** is the legitimate regex fallback, pyyaml **installed but unimportable** is exit 2 naming the real exception, and a probe that cannot tell which is also exit 2. It matters more here than there — the fallback cannot see a YAML *syntax error* at all, so a silent downgrade could hand this gate a **shorter id list** than the criteria file declares, and the criteria that fell out of it would never be checked for coverage. `firm-check-assertions`' `traceability_passes` verb makes this mechanical for eval runs, and treats anything other than 0 or 1 as a hard FAIL on **both** the `true` and `false` expectations. | Same shape as the schema-valid-verdict row: in a live engagement nothing *stops* the Lead presenting the Final gate after a non-zero exit — `CLAUDE.md` and the Definition of Done say it must pass, but that's the Lead honoring a policy document, not a blocked tool call. It also only checks that a criterion is *claimed* covered with *some* evidence string; it cannot judge whether that evidence is any good. One further gap is **known, pinned by tests, and not closed**: if the coverage list holds *two* entries for the *same* declared id, the **last one wins** and the earlier is discarded, so `AC-001: no` followed by `AC-001: yes` passes. The collapse is at least reported now (a `note:` line naming the repeated ids), which is why the reported entry count can be lower than the number of entries in the file, but the resolution rule itself is still positional rather than fail-closed. On the pyyaml-absent path the regex reader remains looser than a real parse in one direction it does *not* close: ids sitting outside the `criteria:` block are still harvested (which over-collects, i.e. errs toward FAIL), and a syntax error is invisible. Install `pyyaml` (see [INSTALL.md](INSTALL.md)) so the exact parser is used. |

The `assertions.yaml` parser still falls back to a regex line-parser when `pyyaml` is absent, but that fallback is **accounting, not tolerant**: it must explain every list item it sees under `assertions:`, and any item it cannot turn into a `- key: value` mapping is treated as a DROP — a dropped assertion is an unrun check, so a single drop fails the whole file with **exit 2** and the offending line quoted. The residual hole is narrower than "a partially-parsed file": it is an assertions file that parses cleanly but declares fewer checks than its author meant (for instance a typo that relocates items outside the `assertions:` block entirely — which *both* parsers then agree are not assertions, so there is nothing for either to report as dropped). An empty, misspelled, mis-indented or truncated assertions file therefore fails the eval loudly rather than certifying a run nobody checked. | Exit 2 catches zero assertions, a YAML syntax error, and — on the `pyyaml`-absent path — any list item the fallback parser could not read, since it accounts for every item under `assertions:` rather than skipping the ones it doesn't understand. | An AI agent cannot merge to `main` or push unless the operator identity is allow-listed | **1, and ONLY against the AI tool surface** | `bin/firm-merge-guard`, registered as a `PreToolUse(Bash)` hook in **both** `hooks/hooks.json` (plugin mode) and `.claude/settings.json` (project mode) — both, because a plugin install only reads the first and a project install only reads the second, so wiring one would silently disable the gate in the other mode. It structurally parses the command line — shlex tokens, operator-split outside quotes, launcher-prefix resolution *including each launcher's own flags and flag values* (`sudo -u X`, `su -c '<cmd>'`, `nice -n 10`, `env -i`, `timeout 60`, `xargs`) — and, where those two readings **conflict**, both are classified rather than one being picked: a flag value can be spelled exactly like a command word (`git` is the conventional service-account name, so `sudo -u git git push` is ordinary phrasing), while `env -i git push` / `command -p git push` / `sudo -n git push` use flags that take *no* value, so there the same token *is* the command. With no per-launcher table of which flags take a value, no ordering gets both right; the guard emits **both readings and gates if either matches**, resolving ambiguity toward blocking, and a prefix ambiguous beyond a bounded number of positions is `cannot-evaluate` rather than a dropped reading, `bash -c` matched as a pattern rather than a fixed spelling (`-ec`/`-xc`/`-lc`), multi-call shell dispatchers (`busybox sh -c '<cmd>'` — treated as a *launcher* of the applet, not as a shell, because reading `sh` as the shell's own operand made it look like a script file), here-strings **including one piped onward to a shell in a later segment** (`cat <<< '<cmd>' | bash`, by the same any-segment-is-a-shell rule the heredoc uses), process substitution as a command boundary rather than a redirection (`cat <(git push origin main)`), quote/escape normalisation of the **subcommand and flags** as well as the command word (`git $'push'`, `gh $'pr' merge`), brace groups, shell keywords, leading and fd-prefixed redirections, `$( )`/backtick descent, and a heredoc body whenever *any* segment of the introducing line is a shell (`cat <<EOF | bash`) — and, **only if** the command is on the gated surface (`git push`/`merge`/`pull`/`subtree push`, **`git config` WRITES to `user.email`/`user.name`**, `gh pr merge`, `gh api` writes including the attached `-XPUT` form and `/merges`, `/git/refs`, `/pulls/N/merge`, `gh release create`, `gh repo sync`), resolves **two** identities — `gh api user --jq .login` **and** `git config user.email` — and requires **both** to appear in the single policy file `agent-firm/policy/merge-authority.yaml`. `git config` identity **writes** are on the surface (reads are not) because the second identity axis is a plain string the restrained actor can set: a control whose only input is a value the caller may rewrite is not a control. Correspondingly, the block message states the problem and does **not** print a runnable `git config --global user.email <listed value>` remedy, which is what it used to do. Three-way exit contract (0 allow-listed / 1 resolved-but-not-allowed / 2 cannot-evaluate) and the hook caller blocks on anything non-zero; the embedded checker exits 3 for a refusal so that a `python3` dying with status 1 cannot be misread as a decision. **An exit status alone no longer authors a decision at all**: the checker prints a proof-of-execution sentinel on stdout and the wrapper honours `0` (permit) or `3` (refuse) only if the sentinel names the same decision. An exit code is a number any `python3` on `PATH` can return without running a line of the check — a stub exiting 3 was reported as a refusal, and a stub exiting **0** was reported as a **permit**, which was a fail-open (a `python3` shim that ignores stdin exits 0). Both are now `cannot-evaluate`; stderr is never captured, so the block message still reaches the agent verbatim. The script's own waits are bounded at 8 s (`gh`) + 4 s (`git`) + 2 x 1 s kill grace = **14 s worst case** under the registered 30 s hook timeout, and a test parses those constants out of the script and out of *both* hook registrations and fails if the inequality stops holding — a hook that overruns its framework timeout does not block. Every indeterminate path is a BLOCK: no network, `gh` absent, `gh` unauthenticated, empty/malformed `gh` output, `user.email` unset, allowlist missing/unparseable/empty/wildcard/unknown-key, no usable YAML parser, an unlexable command, an unrecognised hook payload. The blocking mechanism was **measured, not assumed**, against Claude Code 2.1.220 with a probe hook: exit **2** blocks the tool call and returns stderr to the agent (it registers as a real permission denial), while exit **1** is a *non-blocking* error and the probe command **ran** — so the adapter collapses every non-zero result to 2. `run.jsonl` gets a `merge_guard_block`/`merge_guard_permit` event naming the command and both identities. | **It is client-side and bypassable by anyone with repo write access** — edit the script, delete the hook entry from either settings file, rewrite the git identity **as a file** (`.git/config`, `~/.gitconfig`: the `git config` *command* is gated, the *file* is not, and a `PreToolUse(Bash)` hook never sees the Edit/Write tools at all), or run `git` in a terminal outside the AI tool. That third route was previously worse and is worth stating precisely, because an independent review exercised it end to end: the guard's own block message printed `git config --global user.email <a value read out of the allowlist>`, that command was gated by neither the guard nor `ask`/`deny`, and running it flipped block to permit in **one un-prompted Bash call, dictated by the control to the exact actor it restrains**. The command is now gated and the message no longer prints it, so the remaining route needs a file write rather than a one-liner — still AI-reachable through `Edit`/`Write` or a shell redirect, still disclosed as a gap by `--surface`, and still not something a client-side control can close. It is **not** a security boundary, **not** branch protection, and it **cannot** provide a required PR review; only GitHub can (see [BRANCH-PROTECTION-RUNBOOK.md](BRANCH-PROTECTION-RUNBOOK.md)). Its scope is exactly "stop an AI agent doing this by accident or on its own initiative", not "stop a determined human". It sees only the **Bash tool**: a push from Python/Node, from an MCP server that talks to the GitHub API, or from a `git` alias whose definition is invisible in the command string, is not covered. The launcher handling is generic in the *flags* but the launcher *names* are a list, so an unlisted launcher (`mywrap git push`) is a disclosed gap, as is a launcher whose command operand follows a positional it consumes (`flock /tmp/lock git push`, `chroot /newroot git push` — note the neighbouring launchers whose operands are *flags*, such as `nsenter -t 1 -m /usr/bin/git push` and `setpriv --reuid=1000 git push`, **are** covered, so the gap is a shape and not a set of names), as are container/VM/remote launchers (`docker run ... git push`, `ssh host 'git push'`) where the command runs under a different filesystem and identity than the one this guard resolves, as is the dashed builtin form (`git-push`, `git-config --global user.email`) and third-party `git-*` porcelain (`git-lfs push`) whose command word is not `git`, and so is a command string assembled at run time — including `bash <(echo 'git push')`, where the gated text is the *output* of the substitution rather than its contents (the contents *are* covered) — `firm-merge-guard --surface` prints the covered set and the known gaps side by side, and `tests/test-merge-guard.sh` asserts the gaps *as gaps* so the list cannot drift from the behaviour. Both identity sources are configuration, not credentials: `gh` proves control of a token but is not what an SSH push authenticates as, and `user.email` is a string anyone can set. Finally, because this repo is simultaneously the plugin source and the project, both registrations fire, so a gated command pays two `gh` round trips (~1 s) and logs two events; deliberately not cached, because a cached PERMIT is a fail-open surface. |

Fixing it is a behaviour change to a CI-path gate and belongs in its own work-order with its own tests. (4) The suite tests the scripts; it cannot test the tier-4 rows, because there is nothing to test. |

## What this means in practice

Rows marked tier 4 are not weaknesses unique to this codebase — they're the honest baseline for any
system that ultimately runs on a model following instructions. The firm's actual strategy, stated in
`CLAUDE.md` as "defense in depth," is that the tier-1/tier-2 rows exist specifically to bound the
blast radius *when* a tier-4 claim fails, not to make tier-4 claims unnecessary. Read this table as a
map of where that boundary actually is today, not as a list of things to feel bad about.

When you add a new claimed invariant, add a row here in the same pass — a claim without an entry here
is, by default, tier 4 until proven otherwise. That instruction is itself tier 4: nothing scans the
repo for claims and diffs them against this table, and it has already been missed at least once (the
traceability, no-self-approve and regression-suite rows were backfilled later, not written with the
code). So the table's *completeness* carries strictly less weight than any individual row in it.
